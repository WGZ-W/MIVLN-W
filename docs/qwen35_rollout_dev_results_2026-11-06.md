## 3. 首次错误与传播原因

### 固定中文禁区消息被误判为插入子目标

全部五次错误来自 `subgoal_then_replace` 的中文变体。该序列先插入并完成深色沙发，再将原目标替换为浴缸，
第三轮要求“继续原任务，避开蓝色区域。”，正确更新为 `add_avoid_region(region_blue)`。
history 却输出 `insert_subgoal`：

- 三次将 subgoal 和 resume_goal 填成相同目标，契约拒绝，状态保持原样，因此没有加入蓝色禁区。
- 两次生成合法但语义错误的插入，把岛台或餐桌设为临时目标、浴缸设为恢复目标，实际改变了目标与挂起栈，同时漏掉蓝色禁区。

可直接确认的问题是当前消息的操作类型识别错误。输出中重新出现了先前的原目标及插入/恢复结构，
提示历史中的任务阶段可能干扰当前消息解释；该内部机制只是待验证的解释，不能从最终 JSON 直接证实。
同一句蓝色禁区消息在另一个序列的较后位置没有失败，英文变体也全部正确，因而不能概括为“所有历史输入都不能理解禁区”或“中文整体无效”。

### 一次错误导致后续正确参考更新无法执行

例如 `da178fc79acd0dd35df20b8fb__history`：

1. 插入深色沙发并完成，恢复岛台；随后正确改去浴缸。
2. 第三轮本应新增蓝色禁区，模型却插入岛台，实际状态变成活动目标 island、挂起目标 bathtub，蓝色禁区仍为空。
3. 第四轮输出正确参考 `bathtub→sofa_light` 替换，但实际目标已经是 island，执行器因此拒绝。
4. 第五轮正确加入红色禁区，没有补回此前漏掉的蓝色禁区。
5. 第六轮按参考输出 sofa_light→island，又因实际目标仍为 island 而被拒绝。最后目标恰好与参考一致，但挂起栈、禁区和取消记录仍错。

这个案例同时说明了两种传播：有效但错误的更新会改变后续实际状态；被拒绝的更新也会因遗漏必需约束留下持续影响。
执行器拒绝非法变更保护了状态完整性，但没有自动纠正语义错误或重放漏掉的用户请求。

### 结构化输入的优势与本轮限制

state 每轮明确提供当前目标、挂起栈和约束，在这批轨迹中六轮均为 24/24 正确；错误来源较集中的 history 则需要从请求和反馈重新整理任务阶段。
本轮结果支持“提供实际维护的结构化状态，可提高这些连续明确更新的可靠性”，且没有依赖每轮正确历史状态重建。

两种模板的 history 更新及状态正确数分别为 72/72、52/72；中英文分别为 52/72、72/72。
但只有两个序列模板，五条失败集中于同一句中文消息的同一位置，不能当作五个独立语义现象证明普遍优势。
history 的提示还新增了真实执行反馈，与旧单步实验不同，不能直接比较旧分数和本轮分数推断纯粹的连续长度效应。

两模式的合成完成与恢复均为 24/24，且受影响序列的完成事件发生在首次错误之前，因此本轮没有显示恢复能力的模式差异。
state 没有自然出错，也就尚未观察它面对错误状态时如何恢复。
完成通知仍只是文本夹具，没有测量距离、图像或实际导航，这些成绩不代表 HSSD 导航成功。
