当前项目的任务协议、数据审核、事件执行和独立评测已经有实质实现，但仍是单场景的 Benchmark 原型。正式跨场景划分、统一参赛接口、公开提交评测和社区维护规则尚未建立；另外，Oracle 三类介入已验证，真实语言模型的导航闭环目前只完成了目标替换。
指标上有一个重要区分：当前 dynamic_success 检查目标、约束、顺序和步数；HSSD 的联合成功再加入朝向与实例可见性。模型更新正确率、调用耗时和证据完整性也分别记录。这些分项能解释失败原因；正式发布时还需要统一跨协议指标，并补齐跨场景测试和外部提交规则。
这个项目的 Benchmark 可以概括为：

> 在机器人持续导航的过程中，改变任务要求，测试机器人能否理解更新、保留仍有效的要求，并从当前位置完成更新后的任务。

它需要同时交付任务规则、数据、运行环境、评价器和可复现对照。当前项目已经形成了单场景、可独立审计的 Benchmark 原型；跨场景数据、完整视觉导航和面向外部研究者的公共评测体系还需要补齐。

1. 问题定义：这个 Benchmark 究竟测什么

核心研究对象是导航过程中发生的任务变化，以及机器人对这些变化的适应能力。

例如，机器人原本前往岛台，执行途中可能收到三种消息：

| 介入类型 | 例子 | 正确行为 |
|---|---|---|
| 目标替换 | “不用去岛台了，改去沙发。” | 取消岛台，从当前位置前往沙发 |
| 新增禁区 | “继续去岛台，但不要经过那片区域。” | 保留岛台目标，调整路线 |
| 子目标插入与恢复 | “先去浴缸，再继续原来的任务。” | 暂停原任务，完成浴缸任务后恢复 |

三类任务分别测试取消、保留和恢复。最终到达某个物体，只能说明部分执行结果，还要检查目标是否有效、路径是否违规、任务顺序是否正确。

项目第一版的范围已经比较明确：

- 静态家庭场景、单机器人、文本指令。
- 环境提供第一人称 RGB-D；不同评测轨道使用的信息不同。
- 离散移动、转向和 STOP。
- 每个 episode 为零次或一次介入。
- 介入在动作之间投递，不重置位置、朝向和执行历史。
- 子目标协议额外引入 COMPLETE_SUBGOAL，经实测完成验收后恢复原任务。

这些规则见任务定义 (docs/task_definition.md)。

这里还需要区分两个研究层次：

| 评测轨道 | 测试能力 | 信息边界 |
|---|---|---|
| 任务更新轨道 | 是否理解介入并正确更新要求 | 可提供公开候选和规定的任务上下文，固定导航后端 |
| 端到端导航轨道 | 是否通过视觉、语言和历史完成整个任务 | 不提供正确目标坐标、完整地图或结构化参考更新 |

目前主要完成的是第一条轨道的基础闭环。 Qwen 预测更新，后端使用已知坐标和网格导航；初始目标也已经有符号绑定。因此当前成绩评价的是介入更新，尚未覆盖初始语言理解、视觉目标发现和自主探索的全部过程。

完整 MI-VLN 愿景中的机器人主动求助、等待回复、过期回复处理和双向交互，属于后续扩展。当前“异步介入”主要体现为执行途中到达的新事件，模型回调仍同步阻塞在下一动作之前。

2. 基础设施：怎样保证不同方法运行在同一套规则下

完整 Benchmark 应形成下面的运行链条，其中公开提交和社区反馈部分尚待建设：

    A[任务协议] --> B[审核后的场景与任务]
    B --> C[事件调度与仿真]
    C -->|轨道允许的输入| D[被测方法]
    D -->|动作或更新| C
    B -->|独立任务真值| E[评价器]
    C -->|实际轨迹与执行证据| E
    E --> F[结果报告与公开评测]
    F -->|质检反馈| B

项目目前的基础设施可以分成六层：

| 层次 | 当前项目中的实现 | 作用 |
|---|---|---|
| 仿真环境 | Habitat-Sim、HSSD、导航网格、传感器和动作配置 | 提供可重复执行的物理环境 |
| 任务与事件 | mivln/task_state.py、事件引擎 | 管理有效目标、约束、挂起任务和事件投递 |
| 模型接口 | 公开请求、严格解析、事务式更新 | 将语言预测接入执行，失败时保留真实状态 |
| 数据工具 | 目标预览、审核、任务采样、时机生成 | 生成有证据支持的任务 |
| 实验执行 | 单任务、批量、独立汇总和视频入口 | 保留全部计划位置与失败结果 |
| 工程验证 | 单元测试、假模拟器测试、原始证据复算 | 检查任务语义和执行一致性 |

其中最重要的设计，是将下面三种状态分开：

- 环境状态：机器人实际在哪里、看到了什么。
- 评价器真值：任务实际上要求完成什么。
- 策略状态：机器人自己认为应该做什么。

策略可以理解错误，评价器仍按真实要求评分。例如 Ignore 继续前往旧目标时，评价器不能跟着它把旧目标重新判为正确。

目前还具备几项有价值的可复现机制：

- 记录场景、网格、配置、提示、代码和原始文件哈希。
- 保存实际模型请求、原始响应和状态变化。
- 从轨迹重新计算距离、违规和完成情况。
- 区分任务失败、模型调用失败和证据不完整。
- 输出目录防覆盖，旧结果可以保留原貌供重审。

正式对外发布还需要补齐：

1. 统一的 Agent 适配接口，方便外部方法接入。
2. 可迁移的资源定位和下载校验工具；当前部分清单依赖本机绝对路径。
3. 清晰的环境锁定、安装检查和版本兼容说明。
4. 自动化测试与持续集成。
5. 评分器版本管理，使修复后的新结论与历史成绩可追溯。

Benchmark 应允许方法采用不同的内部记忆或任务表示；统一的是输入权限、动作规则和评价标准。

3. 数据生成：怎样构造有代表性、能够验证的任务

当前项目的数据生成已经具备完整的原型流程：

场景核验 → 实例审核 → 停止点检查 → 基础任务 → 参考导航 → 介入生成 → 自动验收 → 人工复核 → 清单冻结。

具体包含以下工作。

首先，确定目标究竟是哪一个物体。当前使用模板和源实例索引标识目标，并保存审核描述与视觉证据。类别标签只能说明“这是床”，不能单独证明“这是指定的那张床”。

其次，确定合理的停止位置。停止点需要位于可达网格上，并检查楼层、遮挡和可见性。当前的 0.3 m 阈值指到配置停止点的导航距离，不能解释为离物体表面 0.3 m。

然后构造基础任务，固定：

- 场景和资产版本。
- 起点、朝向、随机种子。
- 原目标与可能的新目标。
- 动作预算及终点协议。

介入还必须对后续行为产生实际影响：

| 类型 | 数据有效性需要保证什么 |
|---|---|
| 目标替换 | 新旧目标有实质区别，更新后仍可完成 |
| 禁区 | 禁区与路线有关，同时存在合法替代路线 |
| 子目标 | 临时目标能够完成，之后仍可恢复原任务 |

语言标注与结构化真值也要分工明确：语言描述提供给策略，结构化更新供评价器使用。当前主要使用明确模板，后续需要增加经过审核的自然表达、历史依赖和同类实例描述。

目前的数据规模应这样理解：

- 已审核一个 HSSD 场景中的床、浴缸、岛台、沙发和餐桌实例。
- 有 10 个固定基础任务。
- 不同时机、条件和重复验收会产生更多 episode。
- 100 个 episode 不等于 100 个独立基础任务。

正式数据集还需要扩大场景和语言覆盖，并建立场景隔离的划分。同一基础任务的全部分支、时机和语言改写，应放在同一划分，防止任务泄漏。

另一个需要统一的细节是介入时机：当前目标替换使用参考轨迹的剩余距离变化，子目标协议使用累计行程比例。正式发布应标明各协议的含义；跨策略比较还需要明确外生时刻或状态窗口规则，不能把不同策略的“第 30 步”默认当作同一个空间状态。

当前生成管线见HSSD 语义数据说明 (docs/hssd_semantic_dataset.md)。

4. 指标设计：怎样区分理解正确、执行成功和证据可信

这个 Benchmark 需要分层评价。

| 评价层 | 需要回答的问题 | 当前对应内容 |
|---|---|---|
| 证据完整性 | 结果能否被独立复核？ | 哈希、日志、事件投递、轨迹和观测检查 |
| 更新正确性 | 理解了什么更新，引用是否正确？ | 操作、目标／区域标识、预测状态检查 |
| 任务完成 | 是否完成最终有效要求？ | dynamic_success |
| 语义终点 | 是否停在正确位置并面向、看到指定实例？ | HSSD 联合成功 |
| 效率与响应 | 为适应更新付出了多少代价？ | 路程、动作、介入后效率和回调耗时 |
| 失败归因 | 错误发生在哪一阶段？ | 调用、更新、导航、证据问题 |

当前核心任务成功要求：

> 在预算内执行 STOP，完成有效目标，满足生效约束和子任务顺序。

HSSD 终点协议进一步检查朝向和实例可见性。可以表达为：

Sⱼₒᵢₙₜ = S_{dynamic} ∧ S_{facing} ∧ S_{visible}

因此，integrity_passed=true 表示结果可信，不表示任务成功；完整记录的错误预测仍然是有效实验结果。

三类任务还需要各自的专项指标：

- 目标替换：更新正确率、取消目标误停率、新目标完成率。
- 禁区：目标保留情况、约束违反率、首次违规位置，以及满足约束后的完成率。
- 子目标：B 完成率、A 恢复率、B→A 顺序成功率。

禁区检查目前使用实际运动线段，并考虑机器人半径和楼层，避免只看采样点而漏掉穿越。子目标完成也需要独立测量证据，不能仅凭策略声明推进评价真值。

效率指标同样要匹配任务：

- 无介入任务可报告普通 SPL。
- 目标替换可从实际介入位置计算介入后 SPL。
- 禁区需要遵守约束的最优路径。
- 子目标需要满足 B→A 顺序的最优代价。

后两类当前没有统一的最优效率定义，代码没有将普通无约束最短路误标为它们的 SPL。

响应时间也分两种：response_latency_steps 描述动作步上的响应，model_callback_seconds 记录含 HTTP 和日志的墙钟时间。当前回调发生在动作前，步延迟为零不代表推理耗时为零。

对照实验的含义也必须固定：

| 条件 | 主要用途 |
|---|---|
| 无介入 | 测基础导航能力及原任务代价 |
| Oracle | 验证任务可完成，提供特权参考 |
| Ignore | 检查系统能否识别未处理更新的错误行为 |
| 实际模型 | 测语言更新驱动执行的表现 |

Oracle/model 与 Ignore 可以在同一个更新后的任务真值下比较；无介入分支的成功条件不同，不能直接用两者成功率差值代表介入收益。

当前两候选批次的模型更新和闭环均为 10/10，证明了这批任务的链路有效。五候选实验用于进一步检查目标选择；更广泛的方法优势仍需要语言、场景及实际方法对照。结构化状态的研究也应区分模型贡献与共享状态机自动保证的字段保留。

核心评分实现见评价器 (mivln/evaluator.py)。

5. 社区运营：怎样让别人能够使用、比较和长期维护

这一部分目前主要还是待建设。已有开发约定和实验文档，但仓库尚未形成在线榜单、隐藏测试提交服务和完整的公开发布制度。

可以按以下产物逐步建设：

| 社区产物 | 本项目应包含什么 |
|---|---|
| 任务规范与数据卡 | 任务范围、信息权限、场景来源、采样／标注过程、划分、偏差和限制 |
| 发布包 | 配置、标注、清单、下载校验工具、基线、评分器和版本说明 |
| 快速上手 | 安装检查、小型公开样例、一次完整运行和结果解释 |
| 提交规范 | 方法适配方式、必需文件、计算预算、缺失与异常处理 |
| 分轨道成绩表 | 任务更新与端到端分开，按介入类型、场景和成本报告 |
| 维护流程 | 错误任务报告、标注复核、评分器修复和历史成绩重评规则 |
| 引用与贡献说明 | 贡献入口、引用信息，以及代码、标注和场景资产的授权边界 |

公开评测可以分阶段推进：

1. 先做公开开发集和本地评测：让外部研究者能够复现基线、提交预测并理解错误。
2. 再做隐藏测试评测：冻结测试真值，明确提交次数、调参边界和模型信息。
3. 最后考虑在线榜单或挑战赛：同时记录成功率、约束与顺序指标、计算成本和运行版本。

任务更新的单步预测可以使用 JSONL 提交。连续状态和导航轨道更适合提交 Agent 适配器或可重运行程序，由独立环境执行和评分。

社区维护还要处理两类不同问题：数据本身不合理，以及方法未完成有效任务。前者需要审核和版本化修订，后者应保留为失败。当前子目标阶段已经遇到过检查器误判并保存独立重审证据，这类经验需要转化为公开的更正规则。

如果未来增加主动求助，还需要另行规定人类帮助预算、回答信息量、回复延迟和缺失条件，并记录帮助生成过程，才能比较不同方法的交互收益。

当前最实际的推进顺序是：完成五候选实验 → 接通禁区和子目标的模型闭环 → 冻结统一协议与跨场景数据 → 补齐视觉导航及公共评测。 第一阶段可先发布可信的任务更新轨道，端到端轨道随后完善。
