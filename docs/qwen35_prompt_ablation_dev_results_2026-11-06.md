## 3. 原因：输出显示了什么

### 拒绝说明没有成为可靠的可回答性判断

新增提示明确要求多个匹配输出 `ambiguous_goal`，但公共候选中的 `sofa_light` 和 `sofa_dark` 都具有“沙发”别名，
模型在“改去沙发。”的三个模式下仍全部输出 `status=ok`，共 36/36 条。latest 的 24 条隐式旧/恢复目标请求也全部输出 `status=ok`。
一条不符合契约的 latest 猜测仍是错误输出，不是正确拒绝。

例如 `r400a6a1495b0036e3ace3da5__latest` 只有“先去深色沙发，再继续原任务。”，没有原目标上下文，
模型仍填写 `resume_goal=table`。这直接表明提示中的“缺少依据时拒绝”没有在这些输出中得到执行。
代码目前只是向系统提示增加检查说明，没有增加独立的候选匹配结果或执行前语义门控；它不会自动运行一个新的拒绝算法。
未知物体拒绝的局部改善说明提示会影响输出，但不证明模型已可靠遵循所有检查步骤。

### 状态一致性保护无法判断消息是否允许该目标

state 的歧义请求给出了正确当前目标，因此猜测的新目标容易通过执行器的成员资格和旧目标一致性检查。
例如 `r11dd21436f18c430a8ceb1b2__state` 的当前目标是 bed，消息仅为“改去沙发。”，
模型输出 bed→sofa_dark；引用都合法、旧目标也匹配，更新可以应用，但消息没有指定深色沙发，评价仍判错。
拒绝条件下 state 的 12 条歧义更新全部可应用，另有一条未知物体误映射也可应用，共 13/24 条应拒绝请求会通过适配器，与基线相同。

这说明结构化状态帮助确定当前目标，并不自动解决新指代的唯一性。共享执行器能检查格式、候选成员和状态一致性，
不能替代“书架是否被正确解释”“两张沙发是否都符合描述”等语言语义判断。

### 历史跟踪与操作识别仍需分开处理

拒绝条件没有改变历史呈现，history 的旧/恢复目标错误计数仍为 22；该指标仅统计契约合法且操作正确的明确请求。
history 的显式替换从 8/12 降至 3/12，48 条明确更新中原始操作类型错误从 5 条增至 8 条。
例如“不用去金属床了，改去浅色沙发。”被写成 `insert_subgoal(sofa_light, resume_goal=bed)`，保留了本应取消的床。
state 也有一条明确替换被写成子目标插入，使其明确更新从 48/48 降至 47/48。

历史呈现条件虽然把 history 总分提高到 39/72，但显式替换退化至 2/12，其细节见 [历史条件结果](qwen35_history_ablation_dev_results_2026-11-06.md)。
这些输出支持“上下文跟踪、候选可回答性和操作识别是不同错误来源”的判断。
不能仅凭最终 JSON 确定模型内部为何忽略某条说明，也不能据此声称某种注意力或推理机制已被证实。

## 4. 下一步方案与验收

本轮三个条件已经完成，保留提示、输入和评分作为固定结果。下一步建议实现独立的可回答性与操作诊断实验，
让模型从公开信息输出候选匹配集合（允许空集合和多个匹配）、旧/恢复目标的上下文依据及操作类型，再独立评价这些判断。
这样可以区分“候选匹配错误”“没有跟踪最新目标”和“替换/插入识别错误”，再决定是否加入执行前门控。

前提是复用本轮冻结 dev 请求、同一模型与候选，并补充独立的诊断标注、输出契约和评分。
参考标签只能用于评价，不能提供给模型或作为隐藏的正确状态回填。
预期产物是诊断预测、分模块得分及与最终任务更新的关联分析；验收应同时覆盖歧义集合识别、上下文引用和明确操作识别，
后续门控实验还要验证可应用误执行减少，同时明确更新不退化。
**该诊断入口尚未实现，当前没有对应的新运行命令**。现有 test 已被观察，仅用于回归；泛化验证仍需新的冻结语义组。
